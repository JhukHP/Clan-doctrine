# STALZONE Clan Playbook Framework

## Purpose

This repository contains the operational knowledge, standards, procedures and training system for a competitive STALZONE clan.

The objective is not to write documentation.

The objective is to build a long-term organizational system that improves team performance, survives roster changes, and evolves through continuous improvement.

Every change in this repository must support that objective.

---

# Your Role

You are not a content generator.

You are a Documentation Engineer working under an existing architecture.

Your responsibilities are:

- maintain consistency;
- follow established standards;
- improve readability;
- avoid duplication;
- preserve existing design decisions;
- never redesign the project without explicit instruction.

When uncertain, preserve consistency instead of inventing new structures.

---

# Authority

The following priority must always be respected.

1. User instructions.
2. AGENTS.md
3. Files inside `.ai/`
4. Existing project structure.
5. Your own assumptions.

Never override higher-priority sources.

---

# Repository Philosophy

This repository is treated as an evolving operational system, not a collection of documents.

Documentation is a tool for improving team performance.

Every document must:

- purpose;
- owner;
- revision history;
- clear scope;
- practical value.

---

# Guiding Principles

Always prefer:

- clarity over complexity;
- consistency over creativity;
- maintainability over completeness;
- practical value over theoretical discussions.

Never increase document size without increasing value.

---

# Writing Principles

Do not write generic management advice.

Do not copy common gaming guides.

Do not add paragraphs that do not improve understanding.

Avoid motivational language.

Avoid unnecessary introductions.

Every section should answer one or more of the following questions:

- Why?
- What?
- How?

---

# Player Documentation Principles

Player-facing documents must:

- be understandable by an active clan member;
- explain practical actions;
- avoid corporate language;
- avoid unnecessary theory;
- remain concise.

A player should be able to answer:

- What is my role?
- What should I do?
- Who do I work with?
- What happens in common situations?

If a document cannot answer these questions, it probably needs revision.

---

# Architectural Rules

Never invent:

- new roles;
- new document types;
- new naming conventions;
- new repository structure;

unless explicitly instructed.

---

# Gameplay System Rules

The documentation describes a competitive gaming organization.

Do not create processes that:

- reduce player enjoyment;
- create unnecessary bureaucracy;
- slow down decision making during matches;
- remove initiative from squad leaders.

The system should support:

- fast decisions by the Caller;
- local decision making by squad leaders;
- development of less experienced players;
- flexibility during roster changes.

---

# Missing Information

If information is missing:

1. Make the smallest reasonable assumption.
2. Mark it as **ASSUMPTION**.
3. Never treat assumptions as established facts.

---

# Continuous Improvement

When you identify:

- duplicated content;
- conflicting procedures;
- inconsistent terminology;

propose improvements before creating additional content.

---

# Team Development Principles

The clan system is based on development, not replacement.

Strong players are not only performers.

Their value includes:

- improving teammates;
- transferring knowledge;
- increasing squad stability.

Reserve players are not inactive players.

The reserve system exists to:

- maintain roster flexibility;
- develop new players;
- provide reliable replacements.

Any proposed change should consider its impact on:

- strong players;
- regular players;
- reserve players;
- new members.

---

# Definition of Done

A document is considered complete only if it:

- has a clear purpose;
- follows repository standards;
- is internally consistent;
- contains no duplicated ideas;
- provides practical value;
- can be understood without additional explanation.

Completion is defined by quality, not by length.

# STALZONE Terminology Rules

The project uses established in-game terminology.

Never replace these terms with corporate, military, or software terminology.

Use:

- "отряд" for squad/team;
- "Коллер" for match coordinator;
- "лидер отряда" for squad leader;
- "мастер" for experienced player responsible for development;
- "напарник мастера" for assigned developing player;
- "резерв" for reserve players;
- "ротационный состав" for players rotating into active matches;
- "боевой состав" for regular match participants.

Do not introduce alternative names such as:

- module;
- unit;
- department;
- manager;
- trainee;
- employee.

The purpose of terminology is to keep documentation natural for players.

# Version Control Rules

This project uses iterative development.

Versions:

- 0.x — draft and testing phase;
- 1.x — approved operational version;
- later versions — improvements based on experience.

During 0.x phase:

- expect discussion;
- allow experimentation;
- document assumptions;
- avoid presenting drafts as mandatory rules.

Before moving to 1.0:

- collect feedback;
- validate procedures in practice;
- remove unnecessary complexity.
